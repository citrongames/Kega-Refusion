UMK3H and UMKT music cartridge compatibility

Scope and identification
------------------------
The core selects music hardware behavior when the cartridge is opened.
Up to 10 MiB, the normal linear map already covers all sample addresses.
For larger ROMs with product GM T-097146-00, the core checks two structures:

* The older player calls a selector for two Z80 drivers. Its sample table has
  12-byte descriptors with 24-bit relative addresses. A descriptor pointing
  to a backed sample beyond the linear area enables the packed map (H13/H14).
* The newer player has 68000 upload code in a small region near 7F0000. The
  detector follows the loader's source address and recognizes the Z80 program
  that sets up the YM2612 DAC. This enables the packed map and the protected
  driver handoff described below (H15 through H23).

Names, header checksum and per-version CRCs are unused. The detection runs
once on ROM load and needs no heap buffer. Unsupported revisions that relocate
the entire loader region or use different driver code require further analysis.

Correct memory map
------------------
The appended music is raw unsigned 8-bit PCM packed around hardware windows:
  CPU A80000-BFFFFF -> file A00000-B7FFFF
  CPU C80000-DFFFFF -> file B80000-CFFFFF
A00000-A7FFFF and C00000-C7FFFF keep ZRAM/control/VDP decoding. Both processors
use the same mapped, read-only ROM pages. All embedded track pointers fit the
13 MiB image with this mapping; they were not evidence of missing ROM data.
Only banks with data in the image are mapped. The map is restored after
power/reset, TMSS changes and native state load.

Reference: static disassembly of the supplied-era Gens 13 MiB modification,
https://dlf.emu-land.net/megadrive/GensRR_11_15MHz_CPU_13Mb_ROM_Kaillera.zip
Archive SHA256 3b5f09cbc7173ac324aa725b4c5576154fe8ec3bd69cd3254bd42a4684e6e593.
The byte-read dispatch table at VA778640 maps A8/B0/B8 to functions
5049A0/5049C0/5049E0 and C8/D0/D8 to 504A00/504A20/504A40, with the packed
file offsets above. A0 remains control and C0 remains VDP. The binary was
inspected, not executed. No third-party binary or ROM code is committed.

Sound-driver replacement race
-----------------------------
A bounded native trace caught the original-driver upload at frame 1737:
68K PC3D7680 writes F3 to ZRAM[0] while Z80 PC is still0039 and BUSREQ is held.
At frame1739 an IRQ releases BUSREQ at PC3D7604 before the intended reset at
PC3D76CC. Z80 executes the newly replaced code from the old PC, corrupting RAM.
The eventual reset starts an already damaged driver. Timing changes determine
whether this produces a hang, a held tone or noise; suppressing illegal bus
accesses cannot repair the corrupted program.

For this identified ROM, a 68K write to the ZRAM reset vector marks a pending
handoff. Z80 time and BUSACK keep advancing, but instructions wait until RESET
is asserted. The flag clears after reset synchronization, never before it.
It uses otherwise-free cart.hw.regs[3], already serialized by native states;
soft/hard reset clears it. No new buffers or state trailer are needed. The
recording/network compatibility suffix is umkt-tracks-v4 because mapping and
handoff behavior changed. Other ROMs keep their existing compatibility IDs.

The previous broad read override and tolerant illegal-bus workaround are gone.
Invalid accesses still halt normally; valid hardware decoding is preserved.

Verification and limits
-----------------------
The fixed H23 ROM ran 9000 frames with force_dtack=disabled and no observer
hooks, crossing intro/menu/selection into combat. The original-ROM audio run
used the helper default DTACK setting, earlier Start presses and a forwarding
FM write observer; a later H23 control below explicitly disables DTACK. It also crossed these transitions; Z80 stayed running at all sampled
checkpoints. These are bounded transition/first-fight checks, not a complete
playthrough or proof of every controller timing and ending.

PCM proof: 518600 DAC bytes from the custom PCM program matched the packed
source bytes exactly, with 0 mismatches. Observed track starts:
  frame923: CPU A80000 -> file A00000
  frame1535: CPU C80000 -> file B80000
  frame2571: CPU B90000 -> file B10000
PCM-stream SHA256 aae56000cbd819f2fd5df6d36858e909ef0e917405d0d46db01d4201d17b406f.
This validates the music data itself rather than merely counting nonzero audio.

Generated original-ROM regression:
python3 tests/umkt_tracks_tests.py --core build/linux/core/genesis_plus_gx_libretro.so
Passed: size-only rejection; all packed map boundaries and both CPU views;
read-only ROM; preserved hardware windows; state continuation; IRQ release and
reacquisition of BUSREQ during handoff; save/load while handoff is pending;
soft/hard reset; TMSS remapping; strict illegal bus; unload isolation.
The generated fixture injects the local profile flag to avoid bundling game
code. Positive recognition is covered by the two supplied-image runs.

Correction to earlier reports
-----------------------------
977c7b7 wrongly assumed a linear sample map. Its observer also forced DTACK,
masking the driver-replacement failure. fface47 tolerated illegal Z80 cycles
and could reach combat, but still allowed corruption and read wrong music.
The user's subsequent reports invalidated those claims of a complete fix.
The present change replaces both assumptions with the reference map and the
traced handoff correction. Original-ROM, BIOS and user-save files are retained.

H20/H22 follow-up — 2026-11-04
-----------------------------
H20 (4824) and H22 (5015) share exactly the same driver block (CRC5A6206AE),
which differs from H23; the old detector therefore rejected them. Their 25 PCM
players and original sound-driver upload routines use the same packed map and
handoff protocol. Recognition adds this executable fingerprint, not filenames
or an unrestricted 13 MiB rule. Musical data is checked against each ROM.

H20 SHA256 f6a17366fef3ec8d762677f6b37e2405333e4fd0b4bbbdbb7d1b6dcd99414870
H22 SHA256 82434a5da73e00a1d27ac7aac09024c90121a0311eba1d96e8702cd847cc4db5

The first H20 run exposed an IRQ in the middle of a PCM upload after combat.
GDB caught a discarded write to A00021 at PC7F0278, source7F02D2, zstate1.
Deferring execution alone did not protect remaining 68K writes after the IRQ
released BUSREQ. While an identified upload is pending, A0 now remains writable
by the 68K as well. RESET clears that temporary permission after synchronization.
State load recomputes permission after restoring cart.hw.regs. Hardware access
outside this brief handoff remains unchanged; invalid bus cycles stay strict.

Final runs explicitly applied force_dtack=disabled before the first frame:
  H20: 9000 frames, 578285 PCM writes, 0 mismatches; fight and continue screen.
  H22: 9000 frames, 746104 PCM writes, 0 mismatches; fight and continue screen.
  H23 control: 9000 frames, 573184 PCM writes, 0 mismatches; combat transitions.
All five H20 PCM uploads observed immediately before RESET matched their full
256-byte ROM programs exactly, including the formerly interrupted upload.
The generated fixture checks a bus release DURING copying, restored upload
permission from a pending state, revocation on RESET, and strict-bus behavior.
Its strict-bus assertion now starts with a running Z80 and explicitly disables
forced DTACK instead of relying on the shared helper's defaults.
These remain bounded transition checks, not a full playthrough of each revision.


Collection check, 2026-11-09
----------------------------
40 unique loose BINs from H1 through H23 were opened with neutral filenames
in the Linux core. Mode below is the actual selection after loading. Frames
give the longest run in this audit with that result. A one-frame entry only
verifies loading and identification. Longer runs used scripted pad input.
Early H2/H3/H4/H6 PCM and the H12 alternate driver fit the linear map.
H13/H14 previously stopped waiting on the sound CPU. On both, a packed map
alone resolved the wait. Each ran 3900 frames, and Z80 reads at A80068 and
C80068 and the final 16 ROM bytes matched their physical file contents.
Only the newer player gets the protected handoff and its tracks-v4 ID.
Portable H7/H8/H9 music BINs were unavailable in the EXE distributions.
